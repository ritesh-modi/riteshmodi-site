VECTOR SEARCH · PART 1 OF 2

HNSW, part 1: how it works

Every "find similar" feature, from semantic search to the retrieval step in a chatbot, ends in the same question: which of my millions of stored vectors are closest to this one? HNSW is the algorithm most systems use to answer it in a fraction of a millisecond. Part 1 builds it from nothing: what a graph is, how you search one, why it has layers, and how it is put together. Part 2 tunes every knob on real data.

ACT ONE

Nearest neighbours, and why we settle for "nearly"

The problem, the vocabulary, and the honest cases where you don't need HNSW at all.

01 · The problem

Find the closest points to a query

An embedding is a list of numbers that a model produces for a piece of text, an image or a song, arranged so that similar things get similar lists. Treat each list as a point in space: a vector. Two numbers make a point on a page, which is what the stage shows; real embeddings have hundreds of numbers, but the ideas are identical.

"Similar" becomes "close", measured by a distance: the straight-line (Euclidean) distance, or the angle between two vectors (cosine). Searching means: given a query vector, return the k stored vectors with the smallest distance to it, the "k nearest neighbours". The star on the stage is a query; the ring grows until it holds its 10 nearest points.

The obvious method is exact (or "brute force") search: compute the distance from the query to every stored vector and keep the k smallest. Watch the stage draw a line to all 90 points and count. That count, the number of distance computations, is the cost unit for this whole essay: every method we meet is a way of computing fewer of them.

02 · The trade

Approximate search, and recall

Exact search checks everything, so its cost grows in direct proportion to how much you store: twice the vectors, twice the work. Approximate nearest-neighbour (ANN) search checks only a small, cleverly chosen part of the collection, and in exchange may occasionally miss one of the true nearest points.

How often it misses is measured by recall@k: of the true k nearest neighbours, what fraction did the search return? On the stage, the true 10 are ringed; the approximate answer found 8 of them and returned two slightly farther points instead. Recall@10 is 8/10 = 0.8. Measuring recall needs the true answer, so in practice you compute exact results for a sample of queries once, and compare against them. That sample is called the ground truth.

Recall loss is silent. The search returns 10 plausible results either way; nothing tells you two of them are not the best. That is why later acts measure it on every setting rather than trusting defaults.

03 · The real numbers

When exact search is too slow, and when it isn't

We measured a real dataset: Fashion-MNIST, 60,000 vectors of 784 numbers each, from the public ann-benchmarks suite (which ships the exact answers). One query at a time on one CPU core, exact search took 2.71 ms (median). An HNSW index answered in 0.31 ms with recall@10 of 0.997: about nine times faster, and the gap widens as the collection grows, because HNSW's work grows far more slowly than the collection does.

But look at the third bar. When we sent all 1,000 test queries to exact search together, the library turned them into one big matrix multiplication and the cost fell to 0.059 ms per query, faster than one HNSW query. So be honest with yourself: for tens of thousands of vectors, or for offline jobs that can batch queries, exact search is simple, perfectly accurate and fast. HNSW earns its place when collections are large and queries arrive one at a time, as they do behind a search box or a chatbot.

04 · In code

Exact search and recall, in ten lines

import numpy as np

def exact_knn(X, q, k):
    d = np.linalg.norm(X - q, axis=1)        # one distance per stored vector
    idx = np.argpartition(d, k)[:k]          # the k smallest, unordered
    return idx[np.argsort(d[idx])]            # ... in order

def recall_at_k(found, truth):
    return len(set(found) & set(truth)) / len(truth)

X = np.random.default_rng(0).normal(size=(60_000, 784)).astype("float32")
truth = exact_knn(X, X[0], 10)
print(truth[0], recall_at_k(truth[:8].tolist() + [1, 2], truth))   # 0 0.8

Every stored vector costs one distance computation per query, which the stage counts. Everything that follows is about avoiding most of them.

05 · Inputs and outputs

Act one in a block

in

A collection of vectors, a query vector, a number k, and a distance (Euclidean or cosine).

out

The k closest stored vectors. Exact search guarantees them at a cost of one distance computation per stored vector; approximate search returns most of them (measured as recall@k) at a fraction of the cost.

meaning

HNSW is a way to skip almost all distance computations while keeping recall near 1. Below tens of thousands of vectors, or for batched offline work, exact search may be the better tool.

ACT TWO

Graphs that route

The idea at the heart of HNSW: connect each point to a few nearby points, then search by walking.

06 · The vocabulary

Points, links and neighbours

A graph is a set of points, called nodes, joined by lines, called edges or links. Two linked nodes are neighbours, and the number of neighbours a node has is its degree. A graph says nothing about geometry by itself; it is just a list of "who is connected to whom".

The graph on the stage is a proximity graph: each point is linked to a few points near it. It is the bottom layer of the small HNSW we built for this essay, with 216 links among 90 points, so the average degree is just under 5. Watch one node light up with its neighbours.

Storing those links is cheap: each one is just the number of the node it points to. The trick is in which links you choose, which takes up Acts six and seven. For now, take the graph as given and ask how to search it.

07 · Greedy routing

Walk towards the query, one hop at a time

Here is the simplest possible search on a proximity graph. Start at any node. Look at its neighbours. If one of them is closer to the query than you are, hop to the closest one. Repeat. When no neighbour is closer than where you stand, stop and answer with where you are. This is greedy routing.

It is how you would find a street in an unfamiliar town by asking people: each one points you a bit closer, and you never need a map of the whole town. Each hop costs one distance computation per neighbour you check, so a short walk touches only a handful of the 90 points.

Watch the walk on the stage. It starts at node 35 in the bottom-left cluster and hops 35 → 10 → 5 → 22 → 87 → 81 towards the star: five hops, and only 22 of the 90 points ever had their distance computed. On this query it stopped at node 81.

08 · Where it fails

Stuck in a local minimum

But 81 is not the nearest point. Node 77 is closer to the query. The walk stopped because every one of 81's neighbours is farther from the query than 81 itself, so the rule "hop only if closer" said stop. 77 was reachable, just not through a step that looked like progress. This dead end is called a local minimum: the best spot in its neighbourhood, not the best overall.

How often does this happen? We sent 400 random queries through greedy routing on our graph, each starting from a random node. It returned the wrong nearest point on 51 of them, about one in eight. The stage shows 81's neighbours ringed, each a little farther than 81, with 77 waiting beyond.

Two ideas fix this, and HNSW uses both: look at more than one path at once (Act three), and start each search from a point that is already close (Acts four and five).

09 · Small worlds

Why a few long links matter

In the 1960s Stanley Milgram asked people to forward a letter towards a stranger through friends, and chains were surprisingly short: the "six degrees of separation". Networks like that are called small worlds: most links are local, but a few long ones connect distant regions, so any two nodes are only a few hops apart.

A graph with only very short links is not a small world. A walk would crawl point by point across the map. HNSW's graph keeps some longer links that bridge clusters: 45 of our 216 links connect two different clusters. They glow on the stage. A greedy walk that finds one crosses the map in a single hop. That is the "Navigable Small World" in HNSW's name: a small-world graph that greedy routing can navigate.

10 · In code

Greedy routing on a graph

import math

def greedy(graph, P, q, start):
    # graph: {node: [neighbour, ...]}   P: {node: (x, y)}
    cur = start
    while True:
        best = min(graph[cur], key=lambda n: math.dist(P[n], q))
        if math.dist(P[best], q) >= math.dist(P[cur], q):
            return cur                      # no neighbour is closer: stop
        cur = best

# our 90-point graph, the stage's query, starting at node 35: returns 81 (true nearest: 77)

Short and fast, and wrong about one time in eight on our graph. The next act keeps its speed and fixes most of the wrongness.

11 · Inputs and outputs

A proximity graph (each point linked to a few nearby points), a query, and a starting node.

A node reached by hopping to ever-closer neighbours: found after a handful of distance computations, but stuck in a local minimum on 51 of 400 random queries in our graph.

ACT THREE

Beam search: keeping several paths alive

Instead of betting on one path, keep the best few places you have found and explore around all of them. Its width is called ef, and it is the most important knob in HNSW.

12 · The concept

A short, sorted list with a size limit

Keep a list of the best points found so far, sorted by distance to the query, and never let it grow beyond a fixed size. That size is called ef (for "exploration factor"). Here ef is 4, so the list on the right of the stage has four slots.

The search goes like this. Put the starting point in the list. Then repeatedly take the closest point you have not yet explored, look at all of its neighbours, and offer each one to the list: it gets in if the list has a free slot or if it is closer than the worst point in the list (which then drops out). Stop when the closest unexplored point is already farther than the worst point in the list, because nothing beyond it can improve the list. The answer is the list.

Watch the four slots fill and reshuffle as the search expands. Because it keeps four candidates instead of one, a dead end on one path no longer ends the search. It is like sending four scouts instead of one. This is called a beam search, and ef is the width of the beam.

13 · The bookkeeping

Never check the same point twice

Neighbours overlap: the same point is a neighbour of several points the search expands. To avoid paying for it twice, the search keeps a visited set: every point whose distance has been computed. A point already in it is skipped instantly. On the stage, visited points turn grey.

The grey area is the true cost of a search: every grey point is one distance computation. Real implementations hold the unexplored points in a structure that always hands back the closest one quickly (a heap), and the list of best results in another that always knows its worst member. You don't need the details to use HNSW; just picture two lists: "still to explore" and "best so far".

14 · The example

The same failed query, with a beam of 4

Back to the query where greedy routing stopped at 81, starting again from node 35. With ef = 4, the search does not stop at 81: it still holds three other good points, and keeps expanding them. One of them leads to 77, the true nearest point. Watch the list: 77 enters at the top and stays there. The price was 35 distance computations instead of 22.

Over the same 400 random queries, the wrong answers fell from 51 with ef = 1 to 6 with ef = 4 and 1 with ef = 10. Greedy routing is exactly beam search with ef = 1, so the knob runs smoothly from "fastest, often wrong" to "slower, almost always right".

15 · The price

A wider beam checks more points

Take a new query (the star moves to the middle of the map) and start every search at node 81, near it:

ef = 1 checked 5 points and found the nearest; ef = 4 checked 16 and found the 4 nearest; ef = 10 checked 23 and found exactly the 10 true nearest neighbours. Watch the ten slots fill and the grey area spread as the beam widens.

That is the bargain you will tune in Part 2: a wider beam means more distance computations (slower queries) and higher recall. Even at ef = 10 the search touched 23 of 90 points here. On the 60,000 Fashion-MNIST vectors, an HNSW search with ef = 40 reached recall 0.995 while computing about 474 distances per query, not 60,000.

16 · In code

Beam search, readable version

import math

def beam_search(graph, P, q, start, ef):
    visited = {start}
    todo = [(math.dist(P[start], q), start)]          # still to explore
    best = list(todo)                                 # best so far, at most ef
    while todo:
        todo.sort(); d, c = todo.pop(0)                # closest unexplored
        if d > best[-1][0]:                          # can't improve: stop
            break
        for n in graph[c]:
            if n in visited: continue
            visited.add(n); dn = math.dist(P[n], q)   # one distance computation
            if len(best) < ef or dn < best[-1][0]:
                todo.append((dn, n)); best.append((dn, n)); best.sort()
                best = best[:ef]
    return [n for _, n in best], len(visited)

Real libraries use heaps instead of re-sorting, but the logic is this. With ef=1 it is exactly greedy routing.

17 · Inputs and outputs

ACT FOUR

Layers: the H in HNSW

A beam search is only as fast as its starting point is good. Layers are a cheap way to start close.

18 · The concept

A stack of ever-sparser maps

Think of how you travel to a friend's house in another country: a flight between big airports, a train between cities, a bus across town, then a walk down the street. Each stage uses a coarser network that covers distance quickly, and each drops you close enough for the next, finer one to finish the job.

HNSW builds the same thing out of its graph. Layer 0 holds every point, linked to its near neighbours: the street map. Layer 1 holds only a random fraction of the points, with links among themselves; because there are fewer of them, their links are longer. Layer 2 holds a fraction of those, and so on, until the top layer holds just a handful. A point that lives on layer 3 also lives on layers 2, 1 and 0, with its own neighbours on each. The stage splits our flat graph into its five layers, and the pillars join each point's copies.

This is the Hierarchical in Hierarchical Navigable Small World. The idea comes from a skip list, a classic data structure in which a sorted list carries "express lanes" of every few items, so a lookup can skip ahead before stepping item by item.

19 · Who goes up

Each point rolls a die once

Which points get to live on the higher layers? Nobody chooses. When a point is inserted, it draws a random level: it lands on layer 0 for certain, and climbs one more layer with probability 1/M at each step, where M is the number of links each point keeps (Act seven). With M = 4, a quarter of points reach layer 1, a sixteenth reach layer 2, and so on. In the paper's form, level = ⌊−ln(U) · mL⌋ with U uniform between 0 and 1 and mL = 1/ln M.

Watch the points rise to their drawn levels. In our toy, 90 points live on layer 0, 28 on layer 1, 7 on layer 2, 4 on layer 3 and 1 on layer 4. The 1/4 rule predicts about 22, 6 and 1 for the first three; with only 90 throws of the die, a few extra winners is ordinary luck.

Why random? Because it needs no global view. Each point decides alone, at insertion time, so the index can grow one point at a time forever without rebalancing, and the layers still come out thinning by the same factor on average.

20 · The example at scale

100,000 real points, five layers

We built a real index (faiss, M = 16) over 100,000 vectors and counted the layers. All 100,000 on layer 0, 6,374 on layer 1, 371 on layer 2, 20 on layer 3 and 1 on layer 4. Each layer holds about a sixteenth of the one below, exactly the 1/M the die promises.

The bars are drawn on a log scale, where equal steps mean equal ratios, so the even staircase is the 1/16 thinning made visible. The number of layers grows only with the logarithm of the collection: ten times more points adds less than one layer on average.

The cost of layers is small. About 94% of points live only on layer 0, and upper-layer nodes keep half as many links, so the upper layers add only about 3% more link slots. The one point on the top layer is the entry point: every search starts there. In our toy it is node 83. The first point ever inserted is the entry point until some later point draws a higher level and takes over.

21 · Do layers help?

Measured, with a caveat

We built two graphs over 4,000 random 2-D points, one layered and one flat (layer 0 only), and ran the same searches, both reaching the true nearest point every time. The flat graph, starting from a random point, needed 104.6 distance computations per query; the layered graph, starting at the top, needed 60.6. The upper layers carried the search most of the way in a few long jumps.

Two honest caveats. On our tiny 90-point toy the layers do not pay at all (23.5 distance computations layered against 21.4 flat), because there is no distance to cover. And on high-dimensional embeddings, the gain is much smaller than on flat maps: researchers found in 2024 that a flat graph often searches almost as fast, because a few heavily connected "hub" points do the long-range routing that the layers were meant to do. Layers are cheap insurance, not the main source of HNSW's speed. The main source is the beam search over a well-built graph.

ACT FIVE

A search, start to finish

Now we put layers and the beam together, and follow one query all the way down.

24 · The concept

Greedy at the top, a beam at the bottom

An HNSW search has two phases. In the first, it walks down the upper layers with a beam of width 1, which is plain greedy routing: on each layer, hop to closer neighbours until none is closer, then drop straight down the pillar to the same point on the layer below. Local minima don't matter much here; the only job is to arrive somewhere near the query. In the second phase, on layer 0, it runs the full beam search with width ef and returns the best k.

Follow the query on the stage. It starts at the entry point, node 83, alone on layer 4. On layer 3 it hops to 67. On layer 2 it hops to 81. On layer 1, no neighbour of 81 is closer, so it stays. It drops to layer 0 at 81, already among the query's nearest neighbours, and the beam takes over.

25 · The example

Ten slots on layer 0

With ef = 10, the list on the right fills from 81 outwards. The search finishes holding exactly the ten true nearest neighbours: 87, 81, 27, 22, 7, 82, 32, 77, 72 and 67. In all it computed 37 distances, 14 of them on the way down and the rest on layer 0, out of the 90 an exact search would need.

Over 400 random queries, the layered search with ef = 1 still returned the wrong nearest point 36 times: a better start helps (flat greedy routing missed 51) but does not remove local minima. With ef = 10 it missed none. Starting close and searching wide are complementary: the layers make the start good, the beam makes the finish reliable.

26 · ef and k

Two numbers that are easy to mix up

k is how many results you want back. ef (called efSearch or ef_search in most databases) is how many candidates the search keeps while it looks. They are separate on purpose: a wider search improves the quality of the top k even when k is small. The search returns the best k of its ef candidates.

Because you cannot return 10 results from a list of 4, libraries quietly use the larger of the two: hnswlib searches layer 0 with max(ef, k). We asked it for k = 50 with ef = 5 and it returned 50 results, having searched with a beam of 50. So ef below k is not an error, it is just ignored. Some databases behave differently, which Part 2 covers.

The bars show the price of a wider beam for our query: 19, 30, 37 and 56 distance computations for ef = 1, 4, 10 and 20, all including the 14 spent on the way down. Cost grows with ef, steadily but slower than ef itself, because neighbourhoods overlap.

27 · In code

The real thing, on real data

import hnswlib, h5py, numpy as np

f = h5py.File("fashion-mnist-784-euclidean.hdf5", "r")
X, Q = f["train"][:], f["test"][:1000]
truth = f["neighbors"][:1000, :10]          # exact answers, shipped

index = hnswlib.Index(space="l2", dim=784)
index.init_index(max_elements=len(X), M=16, ef_construction=200)
index.add_items(X, num_threads=12)

index.set_ef(64)                                  # the beam width
labels, dists = index.knn_query(Q, k=10)
print(np.mean([len(set(a) & set(b)) / 10
               for a, b in zip(labels, truth)]))       # 0.9975

This is the whole public surface for most uses: create, add, set ef, query. The dataset is the public ann-benchmarks file; recall@10 is 0.9975.

ACT SIX

Choosing neighbours

Which few points a node links to decides how well the whole graph routes. The obvious choice is wrong.

29 · The obvious rule

"Link to the closest M"

Every node may keep only a few links: M of them (we use M = 4 in the toy). The obvious way to choose is to link each node to its M closest points. Look at node 0 on the stage, with its eight nearest candidates numbered by distance. The closest four are 80, 15, 50 and 35.

The trouble is redundancy. 80 and 15 sit side by side, to the lower left. A link to 15 adds little once you can reach 80: anything reachable through 15 is almost as reachable through 80. In dense clusters this gets worse: every point links only into its own crowd, and the long links that bridge clusters, which Act two showed are what make walks short, never get chosen because there is always something closer at home.

30 · The heuristic

Keep a candidate only if nothing kept already covers it

HNSW's rule: go through the candidates nearest first. Keep a candidate only if it is closer to the node than to every point already kept. Otherwise it lies "behind" a kept point, in that point's shadow, and the kept point already gives a route to it.

Watch it run for node 0. 80, the nearest, is kept. 15 is closer to 80 than to node 0: skipped, in 80's shadow. 50, up and to the right, is kept. 35, below, is closer to node 0 than to 80 or 50: kept. Then 70, 20, 55 and 10 all lie beyond 50: skipped. Node 0 ends with three links pointing in three different directions, rather than four that mostly point one way.

Notice it kept only three, fewer than the four allowed. That is normal: the heuristic often leaves slots empty rather than fill them with redundant links. Both hnswlib and faiss use this rule. The paper also describes two optional extras (adding candidates' neighbours to the pool, and refilling empty slots with pruned candidates); hnswlib uses neither.

31 · What it buys

Fewer links, same bridges, better routing

We built our toy twice, once with each rule. The simple rule made 325 links, 43 of them between clusters. The heuristic made 216, a third fewer, yet kept 45 bridges. The bridges' share of all links rose from 13% to 21%, and the stage shows the two graphs side by side.

Routing follows. With a beam of 5, searches on the heuristic graph found 99% of the true 5 nearest neighbours; on the simple graph, 74.7%. Widening the beam to 20 barely helped the simple graph (77.7%): its searches were trapped inside clusters, not short of candidates.

The caveat: 2-D clusters are the heuristic's best case, and the original paper says its benefit is largest on clustered or low-dimensional data. On high-dimensional embeddings the gap is smaller. But it never hurts, and every serious implementation uses it.

32 · In code

The heuristic in eight lines

import math

def select_neighbours(base, candidates, m, P):
    kept = []
    for c in sorted(candidates, key=lambda c: math.dist(P[c], P[base])):
        if len(kept) == m: break
        if all(math.dist(P[c], P[base]) < math.dist(P[c], P[r]) for r in kept):
            kept.append(c)                  # not in any kept point's shadow
    return kept

print(select_neighbours(0, [80, 15, 50, 35, 70, 20, 55, 10], 4, P))   # [80, 50, 35]

The same function is used twice during insertion, as the next act shows: once to pick a new node's links, and again to trim a neighbour whose list overflows.

ACT SEVEN

Insertion: how the graph builds itself

There is no separate build algorithm. An HNSW index is just a search, run once for every point you add.

34 · The concept

To add a point, search for it

To insert a new point, HNSW asks: "if this point were a query, who would its nearest neighbours be?" and links it to them. Step by step:

1. Draw the point's level (Act four). 2. From the entry point, walk greedily down the layers above that level, as a search would. 3. On each layer from its level down to 0, run a beam search for the new point with width efConstruction, choose up to M neighbours from the results with the heuristic, and link both ways. 4. If a neighbour now has too many links, trim its list. 5. If the point's level is higher than any before, it becomes the new entry point.

efConstruction is the build-time twin of ef: a wider beam during insertion finds better neighbours, at the cost of a slower build. It must be at least M, or the search cannot even supply M candidates to choose from.

35 · The example

Node 81 joins the graph

Here is the real insertion of node 81, the same point that trapped greedy routing in Act two. It drew level 2. At the time, the top layer was 3, so it walked greedily on layer 3 from the entry point and reached 67.

From layer 2 down, it searched with a beam of 16 (our toy's efConstruction) and chose its links with the heuristic: 67 on layer 2; 22, 36 and 57 on layer 1; 27 and 41 on layer 0. Watch each link grow both ways. The results of each layer's search became the starting points for the next layer down.

36 · Overflow

When a neighbour is full

Links go both ways, so 27 gains a link to 81. But 27 already had 8 links on layer 0, which is the cap there. Layer 0 allows 2M links per node (8 in our toy, 32 for M = 16), because it is the layer where searches finish and needs the most routes; upper layers allow M.

With 9 candidates for 8 slots, 27 re-chooses with the same heuristic, over its old neighbours plus 81. It keeps 32, 81, 77 and 22 and drops 12, 4, 6, 36 and 41, ending with four links, not eight, because the dropped ones were in the shadow of kept ones. The same happened on layer 1, where node 36 trimmed to just 51 and 81.

One consequence matters in practice: after trimming, links can be one-way. Node 27 dropped 41, but nothing makes 41 drop 27. And memory is reserved for the full 2M links per node whether they are used or not, which is why M sets memory directly. Part 2 measures it.

37 · Building fast

Threads, order and randomness

Insertion is a search per point, so building costs about as many distance computations as N searches with a beam of efConstruction. On Fashion-MNIST (60,000 × 784, M = 16, efConstruction = 200), one thread took 42.3 s. hnswlib inserts points in parallel with fine-grained locks, and on 12 threads the same build took 4.6 s.

Parallel builds have a side effect: the graph depends on which thread got there first, so two builds of the same data differ slightly. Over three seeds, recall at ef = 64 was 0.9975, 0.9978 and 0.9977. Small, but it means you should compare settings by more than a single build.

Order matters too. Insertion is greedy: early points link to whatever exists when they arrive. We built a 100,000-vector synthetic index twice, once with points sorted by cluster (each cluster arriving all at once), once shuffled. Recall at ef = 64 was 0.944 sorted and 0.985 shuffled. If your data arrives grouped, by date or by customer for instance, shuffle it before a bulk build.

38 · In code

Building, with the knobs named

index = hnswlib.Index(space="l2", dim=784)
index.init_index(
    max_elements=len(X),      # capacity; grow later with resize_index
    M=16,                     # links per node (2M on layer 0)
    ef_construction=200,      # beam width while inserting
    random_seed=1,            # fixes the level draws
)
order = np.random.default_rng(0).permutation(len(X))
index.add_items(X[order], order, num_threads=12)   # shuffled, labelled
# 12 threads: about 5 s.  1 thread: 42.3 s

Passing labels keeps each vector's original id even though we shuffled. The seed fixes the level draws, but with several threads the graph still varies slightly from run to run.

39 · Inputs and outputs

Act seven in a block

in

Recap · part 1

HNSW, from the bottom up

HNSW finds approximate nearest neighbours by walking a graph instead of scanning a list. Read the table from the top: each piece exists because of the one before it.

PieceWhat it isWhat it buys
Proximity grapheach point linked to a few nearby pointsa search touches a handful of points, not all of them
Greedy routinghop to the closest neighbour until none is closerfast, but stuck in local minima about one query in eight
Beam search (ef)keep the best ef points found; expand them; never revisitescapes local minima; ef trades recall for distance computations
Layersrandom levels, each layer about 1/M of the one belowone entry point and long jumps to start close; most useful on low-dimensional data
Neighbour heuristickeep a candidate only if no kept neighbour shadows itlinks spread across directions; bridges between clusters survive
Insertion (efConstruction)search for the new point, link both ways, trim overflowthe index builds itself, one search per point, in parallel

The four knobs

  1. M: links per node (2M on layer 0). Sets graph quality, memory and build time; fixed at build.
  2. efConstruction: beam width while building. Better neighbours, slower builds; fixed at build; at least M.
  3. ef: beam width while searching. Recall against latency; change it any time, no rebuild.
  4. k: how many results you want. hnswlib searches with max(ef, k).

Part 2 turns each knob on real data (60,000 Fashion-MNIST images and 1.18 million GloVe word vectors), then covers memory and quantisation, filters, deletes, scale, a tuning recipe, and how vector databases expose all of this.

Measurements were taken with hnswlib 0.8.0 and faiss 1.15.1 on a 12-core Mac; your timings will differ in the decimals, not the shapes. The toy graph is our own small implementation of the published algorithm.
