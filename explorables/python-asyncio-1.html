Python asyncio, part 1: how it works

Most programs spend most of their time waiting: for a server, a database, a disk. asyncio lets one Python thread wait for thousands of things at once. Part 1 opens the machine all the way down: what the operating system is doing while you wait, how a Python function can pause, and how coroutines, futures, tasks and the event loop fit together. Part 2 puts it to work.

ACT ONE

Why asyncio exists

Before any machinery: what problem it solves, what it does not solve, and a first program you can run in the next two minutes.

01 · Waiting vs working

Your program is mostly waiting

When Python fetches a web page, it spends a few microseconds building the request and handing it to the operating system. Then the request travels across the internet, a server somewhere does its work, and the reply travels back. That can take a whole second. For that second, your program does nothing.

The stage shows three such requests run the normal way, one after another. Each lane is one request; time runs left to right. The orange sliver is Python actually working. The long purple bar is waiting. In this essay asyncio.sleep(1) stands in for a one-second network call, so every number can be checked. Measured on Python 3.12: 3.00 seconds for the three.

Work where the waiting dominates is called I/O-bound (I/O means input/output: network, disk, other programs). Work where the computing dominates, like resizing photos or crunching numbers, is CPU-bound. A call that makes your program sit and wait for I/O to finish is called a blocking call. These three words come back in every act.

02 · Two words people mix up

Concurrency is not parallelism

Concurrency means several tasks are in progress at the same time. A chess master playing twenty boards at a simultaneous exhibition is concurrent: she makes a move on board one, walks to board two while that opponent thinks, and so on. At any instant she is touching one board.

Parallelism means several things are executing at the same instant, which needs several workers: twenty chess masters, or several CPU cores.

The stage shows both. On top, one thread takes short turns at three tasks: concurrency. Below, two cores run two tasks side by side: parallelism. asyncio gives you the first kind, on a single thread. It is the chess master, not the twenty players. That is exactly enough when the opponents (the servers) are the slow part.

03 · The idea

Never stand still while something else is slow

So asyncio's whole idea is: whenever a task reaches a point where it must wait, it says so, and the single thread goes off to run another task. When the wait is over, the task continues from exactly where it stopped.

Watch the three waiting bars slide left until they overlap. The work slivers still take turns on the one thread at the bottom, but the waits now happen together. Measured: 1.00 second instead of 3.00. The total became the longest wait instead of the sum of the waits.

Everything in Part 1 is about two questions that sentence raises. How can a Python function stop in the middle and continue later (Acts four to seven)? And who keeps track of all the stopped tasks and knows when each can continue (Acts eight and nine)?

04 · Run it now

A first program, read token by token

import asyncio, time

async def fetch(n):
    await asyncio.sleep(1)       # pretend network call
    return f"page {n}"

async def main():
    t = time.perf_counter()
    pages = await asyncio.gather(fetch(1), fetch(2), fetch(3))
    print(pages, round(time.perf_counter() - t, 2))

asyncio.run(main())   # ['page 1', 'page 2', 'page 3'] 1.0
async defdefines a function that is allowed to pause. Calling it does not run it yet (Act seven). await"wait for this, and let other tasks run meanwhile". Only allowed inside async def. asyncio.sleepa pause that lets others run, unlike time.sleep, which freezes everything. gatherrun several at once and collect their results in order. asyncio.runstart the event loop, run main, shut everything down. Called once, at the top.

Run it. It prints three pages after one second. Each token is explained properly later; for now, notice that the waiting code reads like ordinary top-to-bottom Python.

05 · What it is not

No help for number-crunching

Replace the waits with pure computation. These tasks never wait, so they are orange from end to end. The stage tries to overlap them and they collide: there is one thread, and each bar needs it the whole time. They slide back into a queue, and the total is unchanged.

So asyncio is the right tool for programs that juggle many slow I/O operations: web servers and API clients with thousands of connections, scrapers, chat and websocket servers, bots that call many services. It is the wrong tool for heavy computation (that needs several processes, measured in Part 2), and it gives nothing to a simple script that makes one request and exits.

06 · What it costs

Cheap, but not free

Is await slow? We timed two hundred thousand calls. A plain function call took 0.092 µs each. Awaiting a coroutine that returns straight away took 0.086 µs: the same. But creating a separate task for each one (a coroutine the event loop runs on its own; Act eight), so they can run concurrently, cost 3.51 µs each, about forty times more.

Three microseconds is nothing next to a one-second network call, and a disaster next to adding two numbers. The rule that follows: make tasks for things that wait; keep fast pure computation as ordinary function calls. And the biggest cost is not speed at all. Once a function is async, everything that calls it must be async too. Act seven calls this "function colour", and Part 2 is largely about living with it.

ACT TWO

Processes, threads and the operating system

asyncio is easiest to understand next to the thing it replaces. So first: what does the operating system already do to run several things at once?

08 · Process and thread

A house and the people in it

When you start Python, the operating system creates a process: a private block of memory that no other program can touch, plus the open files and connections that belong to it. Think of it as a house.

Inside the house lives at least one thread: a worker that executes your code one instruction at a time. A thread owns very little: its own stack (the notepad of the function calls it is in the middle of; Act four explains it) and its current position in the code. Everything else in the house, all the objects and variables, is shared by every thread in it.

A process can start more threads. They share the same memory, which makes it easy to pass data between them, and dangerous, because two workers can grab the same object at once. Watch the house gain two more workers.

09 · The scheduler

The OS hands out turns, and can take them back

Your machine has a few CPU cores and often thousands of threads. The operating system's scheduler decides which thread runs on which core, for a short slice of time. When the slice is used up, it pauses the thread wherever it happens to be, saves its state, and runs another. That forced pause is called preemption, and saving one thread's state to load another's is a context switch.

The key word is wherever. A thread can be stopped in the middle of any line, even halfway through updating a variable. The thread has no say in it. Watch the CPU token hop between the three lanes, cutting bars in arbitrary places.

A thread that is waiting for I/O is not in the line at all. It is asleep inside the operating system, using no CPU, and the scheduler wakes it when its data arrives. Blocked threads cost memory, not processor time.

10 · The GIL

Python's one-at-a-time rule

Standard Python (CPython) adds its own rule on top: the Global Interpreter Lock, or GIL. Only the thread holding the GIL may run Python code. It exists because it makes the interpreter's own bookkeeping simple and fast. Threads pass it around: a running thread is asked to hand it over once another thread has been waiting 5 milliseconds (we checked: sys.getswitchinterval() is 0.005), and gives it up immediately whenever it starts a blocking I/O call.

Watch the single GIL token. Threads doing I/O let go of it while they wait, so many I/O-bound threads overlap nicely. CPU-bound threads all want the token and can only take turns, so on standard Python, threads do not make computation faster. C extensions such as numpy can release the GIL during heavy work and do run in parallel.

Python 3.13 introduced an experimental "free-threaded" build without the GIL (officially supported from 3.14). It does not change asyncio's design; asyncio runs on one thread either way.

11 · Where things can interleave

Interrupted anywhere vs only where you say

Because the scheduler can pause a thread anywhere, two threads updating the same counter can interleave in the middle of count = count + 1: both read 5, both write 6, one update is lost. That is a race condition, and with threads it can happen between almost any two steps.

asyncio flips this. Tasks are never preempted. A task keeps the thread until it reaches a point where it actually pauses, and those points are marked in the code by await. The stage shows the difference: thread lanes cut at random places, asyncio lanes switching only at the marked notches. Races still exist in asyncio, but only across a pause, which makes them far easier to see. Part 2 shows one, and the locks that fix it.

12 · The example

A thousand waits, two ways

We ran the same job twice: a thousand things each waiting one second. With a thousand threads: 1.04 s, and the process's peak memory grew by 34.6 MB. With a thousand asyncio tasks: 1.01 s, and memory grew by 1.5 MB.

Both finished in about a second, because both overlap the waiting. The difference is cost per waiter. Each thread needs its own stack reserved by the operating system (only the pages it actually touches count towards that 34.6 MB), plus kernel bookkeeping and a share of context switches. An asyncio task is an ordinary Python object holding one paused function. That ratio is why a single asyncio process can hold tens of thousands of open connections.

13 · In code

The same thousand waits

import threading, time, asyncio

# threads: the OS schedules, preemptively
ts = [threading.Thread(target=time.sleep, args=(1,)) for _ in range(1000)]
for t in ts: t.start()
for t in ts: t.join()                 # 1.04 s, +34.6 MB

# asyncio: one thread, tasks switch at await
async def main():
    await asyncio.gather(*(asyncio.sleep(1) for _ in range(1000)))
asyncio.run(main())                    # 1.01 s, +1.5 MB

Threads are not wrong. For a handful of blocking calls they are often the simplest tool, and asyncio itself uses a thread pool for blocking code (Part 2). asyncio wins when the number of waiting things gets large, or when you want switching to happen only where you can see it.

ACT THREE

What "waiting for the network" really is

Sockets, file descriptors and readiness: the three operating-system ideas the event loop is built on, and the reason the requests library can never take part in it.

15 · File descriptors

Small numbers that stand for open things

When your program opens a file or a network connection, the operating system keeps the real object to itself and hands you back a small integer, a file descriptor (fd). Every later read or write names that number. Numbers 0, 1 and 2 are already taken at startup: standard input (usually the keyboard), normal output and error output.

A socket is one end of a network connection, and it gets a file descriptor like a file does. In our test, socket.socketpair(), which makes two sockets already connected to each other (handy for experiments), got descriptors 3 and 4. A server socket is created, told to listen(), and each accept() hands back a new socket, with a new number, for one client.

(On Windows sockets are "handles" rather than fds, but the idea is the same.)

16 · Blocking mode

recv() parks the thread inside the OS

Data from the network does not go straight into your program. It arrives in a kernel buffer, a waiting area that the core of the operating system (the kernel) keeps for each socket, whether or not your program is doing anything at that moment.

By default sockets are in blocking mode. Calling sock.recv(100) means "give me up to 100 bytes from the buffer". If the buffer is empty, the operating system puts your thread to sleep right there, inside the call, until bytes arrive. Watch the thread drop into the kernel, the bytes trickle in, and the thread come back up holding them.

For one connection that is perfect. For a thousand it means a thousand sleeping threads, which is exactly Act two's cost. And while a thread is asleep inside recv, Python cannot run anything else on that thread, whatever else is ready.

17 · Non-blocking mode

Ask, and get an answer straight away

Call sock.setblocking(False) and the same recv never sleeps. If bytes are waiting, it returns them. If not, it fails immediately with an exception. We ran it: BlockingIOError: [Errno 35] Resource temporarily unavailable. (35 is macOS's number; Linux uses 11. The meaning is "nothing yet, try again".)

That solves half the problem. A thread is never stuck. But now: when should you try again? Asking every socket over and over in a loop, called busy polling, keeps a core at 100% doing nothing useful. Watch the bounced requests pile up. What we need is a way to ask the operating system once: "wake me when any of these has data".

18 · Readiness

"Readable" means bytes are waiting

A socket is readable when its receive buffer holds at least one byte, so a recv would return without waiting. It is writable when its send buffer has room. Two edge cases matter in practice.

First, when the other side closes the connection, the socket also becomes readable, and recv returns empty bytes: b''. We checked. That is how every network program knows a peer has gone.

Second, sending can wait too. The send buffer is finite. On our socket pair, a non-blocking send of 64 KB accepted just 8,192 bytes, a partial send, and the next one failed with BlockingIOError. A program that sends faster than the network drains has to slow down. That is the seed of backpressure, a pattern Part 2 builds on.

19 · The example

One question for many mailboxes

Picture a post office with a wall of mailboxes. Rather than standing in front of one box all day, or running back and forth opening every door, you ask the clerk: "which boxes have mail?" The clerk answers only with those.

That clerk is a selector. You register sockets with it, then call select(timeout). The operating system wakes your thread when at least one registered socket is ready, or when the timeout passes. We measured both: with no data, select(timeout=0.2) returned an empty list after 0.20 s; after the other end sent "hi", it returned our socket straight away, and recv got b'hi'.

Every operating system has its own version: select everywhere, poll on Unix, epoll on Linux, kqueue on macOS (Python picked KqueueSelector on our machine), and I/O completion ports on Windows, which work differently (you hand over a buffer and are told when it is filled). Python's selectors module picks the best one for you.

20 · The consequence

Why requests can't be awaited

Now the most practical fact in this act. A library like requests opens a blocking socket and calls recv itself, deep inside its own code. When that call waits, your thread is asleep inside the operating system. There is no point at which it hands control back to Python, and no socket registered with any selector. The stage shows the thread vanishing into the OS where the selector cannot see it.

Writing await requests.get(url) makes it worse, not better: the blocking call runs to completion first, freezing the whole loop, and only then does Python raise a TypeError, because the response it returns is not awaitable. Wrapping it in async def changes nothing either: the thread still freezes. Async libraries such as httpx and aiohttp exist because the waiting has to be built differently from the bottom: non-blocking sockets plus a selector. Part 2 shows how to call blocking libraries safely anyway, by moving them to a thread.

21 · And files?

Disks don't fit the readiness model

You might expect files to work the same way. They don't. On Linux, epoll refuses to watch regular files at all; on macOS, kqueue reports a file "ready" whenever it is not at the end. Neither can tell you whether the next read will be served instantly from memory (the operating system's page cache) or will wait milliseconds for the disk.

The stage shows two reads that both look "ready": one comes back instantly from the cache, one stalls on the disk. Because readiness can't predict that, async file libraries like aiofiles simply run ordinary blocking reads in a thread pool. Remember this when you hear "async file I/O": it usually means threads underneath.

22 · In code

A selector by hand

import socket, selectors

a, b = socket.socketpair()            # two connected sockets: fds 3 and 4
a.setblocking(False)
try:
    a.recv(10)
except BlockingIOError as e:
    print(e)                           # [Errno 35] Resource temporarily unavailable

sel = selectors.DefaultSelector()      # KqueueSelector on macOS
sel.register(a, selectors.EVENT_READ, data="a")
print(sel.select(timeout=0.2))         # []  (after 0.20 s: nothing ready)
b.send(b"hi")
for key, _ in sel.select(timeout=0.2):
    print(key.data, key.fileobj.recv(10))  # a b'hi'

Keep this snippet in mind. Act nine's event loop is this select call wrapped in a loop, with a list of timers next to it and a queue of things to run.

ACT FOUR

Iterators, frames and callbacks

Three pieces of ordinary Python that asyncio is built from, and one problem, "callback hell", that explains why it was built the way it was.

24 · The iterator protocol

What a for loop really does

A for loop is shorthand. for x in nums: first calls iter(nums), which returns an iterator: an object that remembers where it is. Then it calls next() on it again and again. Each call returns the next value. When there are none left, next() raises StopIteration, and the loop catches that exception and ends quietly.

We ran it on [10, 20, 30]: iter() gave a list_iterator; three next() calls gave 10, 20, 30; the fourth raised StopIteration. Watch the stage pull the values out one by one and hit the end.

Two things to keep: an iterator is an object you pull values from one at a time, and "I'm finished" is signalled by an exception. Generators (Act five) and coroutines (Act seven) both reuse this exact protocol, so StopIteration will turn up again carrying a return value.

25 · The call stack

Each call gets a notepad

When a function is called, Python creates a frame: a notepad that holds that call's local variables and its current line. When a() calls b(), which calls c(), the frames pile up like a stack of notepads. Python only works on the top one. When c returns, its notepad is thrown away, its local variables die, and b continues where it left off.

A traceback is a printout of this stack. When c divided by zero in our test, the traceback listed the frames from the bottom up: <module>, then a, b, c. The error travelled up through every frame until something caught it, or nothing did.

Here is the problem asyncio has to solve. With ordinary functions, a frame can't be put aside and picked up later. If c needs to wait for the network, the whole stack has to sit and wait with it. Watch the notepads push and pop.

26 · Callbacks

Leave a number, get called back

In Python a function is a value. You can store it, pass it to another function, and let that other function call it later. A function handed over to be called later is a callback. It is like leaving your phone number with a receptionist: you go and do something else, and they call you when your table is ready.

This is the oldest way to write programs that wait without blocking. You start an operation and pass a callback: "when the data arrives, call on_data(data)". Your function returns immediately; the thread is free. Watch the function card being handed to a timer and called when the timer fires. asyncio's event loop, deep down, still works this way: it is a machine for calling callbacks (Act nine).

27 · The problem with callbacks

Callback hell

Now write something with three waiting steps: fetch a page, parse it, save the result. With callbacks, each step's code goes inside the previous step's callback:

fetch(url, lambda page:
    parse(page, lambda items:
        save(items, lambda ok:
            print("done"))))

Watch it nest deeper on the stage. Three things go wrong. The code drifts right and stops reading top to bottom. Local variables from step one are awkward to use in step three. Worst, errors break: if parse fails inside a callback, there is no caller frame to raise the exception into. The function that started the work returned long ago. Every step needs its own error callback, and a forgotten one means a silent failure. This is called inversion of control: your program no longer calls its next step, someone else does.

What we really want is to write page = fetch(url), items = parse(page), save(items) as normal lines, with normal try/except, and have the function pause at each wait instead of blocking. That needs a function whose frame can be put aside and resumed. Act five shows that Python already has one.

28 · A trap worth knowing

Callbacks remember variables, not values

When you create callbacks in a loop, a classic bug appears. [lambda: i for i in range(3)] makes three functions, and calling them returns 2, 2, 2, not 0, 1, 2. We ran it. Each lambda looks up i when it is called, and by then the loop has finished with i equal to 2. This is called late binding.

Two fixes: a default argument, lambda i=i: i, which captures the value at creation (gives 0, 1, 2), or functools.partial(func, i), which packages a function with its arguments ready to call later. asyncio's API is built in the same style: loop.call_soon(func, arg) takes the function and its arguments separately, and its documentation recommends partial over lambdas.

29 · In code

The three ideas, runnable

it = iter([10, 20, 30])
while True:                       # what "for x in [10, 20, 30]" does
    try:
        x = next(it)
    except StopIteration:
        break
    print(x)

import threading, functools
timer = threading.Timer(0.5, functools.partial(print, "called back", 42))
timer.start()                     # returns at once; prints after 0.5 s

The first block is the iterator protocol by hand. The second hands a callback, built with partial, to a timer that calls it half a second later on another thread.

ACT FIVE

Generators: frames that survive

Python has had pausable functions since version 2.2. They were built for producing sequences lazily, and they turned out to be exactly what asynchronous code needed.

31 · The concept

A function with a bookmark

Put the word yield anywhere in a function and it becomes a generator function. Calling it no longer runs the body. Instead it returns a generator object, which is also an iterator. Each next() runs the body until the next yield, hands out the yielded value, and stops there.

The crucial part is what happens to the frame. A normal function's notepad is thrown away on return. A generator's notepad is kept, bookmarked at the yield line, with all its local variables intact. The next next() opens it at the bookmark and carries on.

The stage draws the function as a tape, one box per line, with a playhead. Watch it run to yield, hand out 0, and stop. The function is not finished; it is paused, and it still knows that i is 0.

32 · The example

Three values, then the end

squares(3) yields i*i for i in 0, 1, 2. The first next() runs to the yield and gives 0. The second resumes after the yield, loops once, gives 1. The third gives 4. The fourth resumes, finds the loop finished, falls off the end of the function, and raises StopIteration, the protocol from Act four. A for loop over the generator stops right there.

Nothing was computed ahead of time. Each value was made when it was asked for. This is lazy evaluation. And if you stop asking halfway, the rest is simply never computed. We gave a copy of squares a try/finally that prints "generator cleaned up", took two values from squares(5), and dropped it: Python closed it and the finally block ran.

33 · Proof the frame survives

You can look inside a paused generator

A paused generator exposes its frame as gen.gi_frame, and the frame's variables as gi_frame.f_locals. We paused a generator right after it set total = 5 and looked: {'total': 5}. The variable is sitting there, alive, while the function is not running.

Where does that frame live? Not on the thread's stack, which is reused by whatever runs next. Python stores generator frames on the heap, the general memory area for objects, and the generator object holds onto it. That is why a paused generator can be passed around, stored in a list, and resumed from anywhere. Hold that sentence: in Act seven a coroutine will be exactly such an object, and a scheduler will keep thousands of them in a queue.

34 · Why laziness matters

A million squares: 40 MB or 232 bytes

Build a list of a million squares and Python stores all of them before you use the first. Measured with tracemalloc, which counts every allocation: 40.4 MB. (A popular shortcut, sys.getsizeof(list), says 8,448,728 bytes, but that is only the list's array of pointers, not the number objects it points to.) The generator producing the same million numbers allocated 232 bytes.

The stage fills the list field one dot per thousand items while the generator stays one dot. That is why you can stream a 50 GB log file through a generator pipeline on a laptop. And it is why "return a list" is the wrong answer when the data is large, endless, or arriving over time.

35 · Its life

Four states

inspect.getgeneratorstate() reports one of four states. Created: made, never started (we saw GEN_CREATED). Running: executing right now. Suspended: paused at a yield, frame kept (GEN_SUSPENDED after the first next). Closed: finished or closed.

Watch the token bounce between running and suspended once per value, then land in closed. That bounce is the heartbeat of asyncio: a task spends its life alternating between running (on the thread) and suspended (waiting), and something outside it decides when to resume it.

One rule from PEP 479 (PEPs, Python Enhancement Proposals, are the documents that define language changes): a generator must end by returning, not by raising StopIteration itself. If it does, Python turns it into RuntimeError: generator raised StopIteration (we triggered it), so a stray exception can't silently end a loop.

36 · In code

Writing and driving generators

import inspect

def squares(n):
    for i in range(n):
        yield i * i

g = squares(3)
inspect.getgeneratorstate(g)     # 'GEN_CREATED'  nothing ran
next(g), next(g), next(g)        # (0, 1, 4)
g.gi_frame.f_locals              # {'n': 3, 'i': 2}  the paused frame
list(squares(3))                 # [0, 1, 4]  list() calls next() for you
sum(x * x for x in range(10**6))  # generator expression: no list built

The stage shows list() at work: it calls next() until StopIteration, then gathers the loose values into one list.

ACT SIX

send, throw, close, yield from

A generator that only produces values is half of what we need. To build a scheduler, the outside world must be able to push values and errors into a paused function, and pauses must work across a whole chain of calls.

38 · send()

The window works both ways

Think of the paused generator as a shop with a service window at its yield line. next() takes a value out through the window. gen.send(x) pushes x in through the same window and resumes the function; inside, the yield expression evaluates to x. So x = yield avg means: hand out avg, pause, and when something is sent in, store it in x and continue.

The averager on the stage keeps a running total. Before sending, it must be primed with one next() to reach the window; it hands out None. (Sending first fails: TypeError: can't send non-None value to a just-started generator.) Then send 10 and out comes 10.0; send 20, out comes 15.0; send 60, out comes 30.0. All measured. The state lives in the paused frame's own variables; there is no class.

PEP 342 (Python 2.5) added this under the title "Coroutines via Enhanced Generators". A function that passes control back and forth with its caller like this is a coroutine. That is where asyncio's word comes from.

39 · throw()

Raise an error at the paused line

gen.throw(SomeError) resumes the generator by raising that exception at the yield where it is paused, as if that line had failed. Whatever try/except surrounds the yield gets a chance to handle it.

The surprising part, which we tested: the generator does not have to die. Our averager (the code below) caught the ValueError, skipped the update and looped back to its yield, so throw() returned 30.0, the average it hands out next. Watch the red bolt hit the yield line, get caught, and the playhead carry on.

This is how asyncio cancels a task (Part 2): it throws a CancelledError into the coroutine at the point where it is paused. And it is why a coroutine that catches that error and doesn't re-raise it can refuse to be cancelled.

40 · close()

Closing time

gen.close() throws a special GeneratorExit at the paused line. The generator is expected to let it propagate, running any finally blocks on the way out, which is where cleanup belongs: closing files, releasing connections. Python also calls close() automatically when a paused generator is garbage-collected (freed because nothing refers to it any more); that is what printed "generator cleaned up" in Act five.

The rule: while closing, a generator must not yield again. Ours had a yield inside its finally. Result, measured: RuntimeError: generator ignored GeneratorExit. The stage shows the playhead trying to pause in the finally and being stopped. Async code has the same rule in a new form: cleanup that needs to wait gets special handling, covered in Part 2.

41 · yield from

Handing over the window

Real code is split into functions that call functions. If generator outer wants to run generator inner as one step, yield from inner() connects the caller directly to inner. Every value inner yields goes straight out. Every value sent in goes straight down to inner. Every exception thrown in goes to inner too. When inner returns a value, it becomes the result of the yield from expression.

On the stage, inner does x = yield 1, y = yield 2, return x + y. The caller primes it and gets 1, sends 5 and gets 2, sends 7; inner returns 12, which lands in outer as r. Measured: "inner returned 12". (Under the hood, the return value travels inside the StopIteration exception.)

42 · Why not a loop?

What yield from does that a for loop can't

Couldn't outer just write for v in inner(): yield v? That passes values out, but nothing else. A value sent into outer would land in outer's own yield, not inner's. A throw() would hit outer, not the line in inner that is actually paused. And inner's return value would be lost, because a for loop swallows StopIteration.

yield from forwards all four: values out, sends in, throws in, return value back. The stage compares the two: with the loop, the send bounces off outer; with yield from, it reaches inner. This complete transparency is what lets a chain of generators behave like a chain of ordinary function calls.

43 · The big consequence

One pause suspends the whole chain

Stack three: main does yield from fetch(), fetch does yield from read_socket(), and at the bottom read_socket finds no data and does a plain yield. That yield travels up through fetch and main and out to whoever is driving main. All three frames are now paused in place, kept on the heap.

Later the driver sends a value in. It travels straight down to read_socket, and the whole chain resumes as if nothing happened. Watch the pause signal climb the stack. Now picture the driver at the top as a scheduler holding hundreds of these chains and resuming whichever one has data ready. That is asyncio, and its first version (Python 3.4) was written exactly like this, with yield from.

def averager():
    total, n, avg = 0, 0, None

ACT SEVEN

Coroutines in depth

Python 3.5 (PEP 492) gave pausable functions their own syntax: async def and await. Underneath, they are the generators of Acts five and six, specialised for waiting.

46 · The concept

Calling it does not run it

async def defines a coroutine function. Calling it does not execute a single line of the body. It creates a coroutine object: a paused function with the bookmark above its first line, just like a fresh generator. inspect.getcoroutinestate() reports CORO_CREATED.

This is the single most confusing thing for newcomers, so it is worth saying plainly. fetch() on its own line does nothing at all except make an object. Something has to drive that object: an await inside another coroutine, or the event loop through a task. Watch the stage: the call pops out an object, and the playhead does not move.

A coroutine function doesn't need to contain any await. async def f(): return 5 is legal; it just never pauses, and running it returns 5 (we checked).

47 · You are the loop

Driving a coroutine by hand

A coroutine object has the same send method as a generator. So we can play the part of the task and the loop ourselves. At the bottom of our chain is a tiny function that really pauses: it yields the message "need data" and waits for something to be sent back. On top of it, fetch awaits it, and main awaits fetch.

We call c.send(None). The whole chain runs, main into fetch into the bottom, until the bottom yields. That yield climbs straight back out to us: send(None) returns "need data". The state is now CORO_SUSPENDED; all three frames are paused on the heap. We call c.send("hello"). It travels down to the bottom; fetch upper-cases it; main finishes; and the return value arrives the generator way, inside StopIteration: "got HELLO".

Watch the request climb up to "you" and the answer travel down. Everything an asyncio Task does is a more careful version of these two calls. In asyncio the thing yielded up is not a string but a Future (or, for sleep(0), a bare None), which Act eight explains.

48 · What await means

await: run it here, and pass any pause upwards

result = await fetch() means: run fetch right now, inside this chain, until it finishes, and give me its return value. If somewhere underneath it needs to pause, the pause passes up through me to whoever is driving the chain, and I resume when they send the answer down. It is yield from with a new name, restricted to things that are awaitable: coroutines, objects with an __await__ method (Futures and Tasks have one), and old-style generators marked with types.coroutine.

Errors behave like normal function calls. When parse raised ValueError("bad page") three awaits deep, the traceback listed every frame (main, fetch, parse) and an ordinary try/except around await fetch() could catch it. That is exactly what callbacks could not give us in Act four.

Rules that come with the syntax: await outside an async def is a SyntaxError; awaiting something that isn't awaitable is a TypeError.

49 · The subtle part

await does not always pause

Here is a misconception that trips up even experienced developers: await pauses only if something at the bottom of the chain actually yields. Awaiting a coroutine that just computes and returns is an ordinary function call. Nothing else gets to run.

We tested it. A second task was ready to run. Our main task then did three awaits of a coroutine that never pauses, and the other task did not run in between. It ran only when main reached await asyncio.sleep(0), a real pause. Measured order: "after 3 awaits", then "other ran", then "after sleep(0)". Watch the other lane stay grey through the three non-pausing awaits.

So the precise rule is: no other task runs until the current one reaches a real suspension point. await marks where one might happen. This matters twice in Part 2: it is why code between real pauses is safe from interference, and why a long computation inside a coroutine, awaits or not, freezes everything.

50 · Two classic mistakes

Never awaited, and awaited twice

Forgetting the await. fetch() without await creates a coroutine object and throws it away. No request is sent, and no exception is raised, because making an object is not an error. When the object is garbage-collected, Python prints RuntimeWarning: coroutine 'fetch' was never awaited, a warning, not an error, and your program carries on with the work silently not done. We triggered this exact warning while preparing this essay. Watch the object drift away and turn red.

Awaiting twice. A coroutine object runs once. Awaiting the same object again raises RuntimeError: cannot reuse already awaited coroutine (measured). If you need to run the same work again, call the function again to get a fresh object.

51 · Function colour

Async spreads upwards

A normal function cannot await; only an async def can. So if a low-level function becomes async, every function that calls it must become async too, and every function that calls those, all the way up to the top. Programmers call this function colour: functions are either red (async) or grey (sync), and a red function can only be awaited from another red one.

Watch the tree on the stage: one leaf turns async, and the colour climbs to the root. The top of the tree, the one place where grey calls red, is asyncio.run(). Where you draw that boundary, and how blue and red code call each other safely in both directions, is the main subject of Part 2.

ACT EIGHT

Futures, tasks and the bottom of the chain

What exactly is yielded up when a coroutine pauses, who receives it, and what wakes the coroutine up again? This act answers with the real code paths inside asyncio.

Three loop methods appear before Act nine explains them in full: call_soon(f) runs f on the loop's next turn; call_later(d, f) runs it after d seconds; add_reader(sock, f) runs it when the socket is readable.

54 · Future

A box for a result that doesn't exist yet

A Future is an empty box with three possible states: pending, done (holding a result or an exception), or cancelled. Anyone can register done callbacks on it: functions to run the moment it is filled. It is the coat-check ticket of asyncio: you hand in your coat, get a ticket, and are called when it's ready.

We made one by hand with loop.create_future(), attached a callback, and told the loop to fill it with 42 after half a second. Awaiting it paused our coroutine; after 0.50 s the callback printed "callback sees 42" and the await returned 42. A future can be filled only once: trying again raised InvalidStateError. Watch the box fill and the callbacks fire.

Awaiting a pending future is the real "bottom" of every asyncio chain. Its __await__ yields the future itself up the chain, saying, in effect, "wake me when this box is filled".

55 · Task

The porter that drives a coroutine

A Task wraps a coroutine and drives it, doing exactly what we did by hand in Act seven. Each step calls coro.send(None) (or coro.throw(exc) to deliver an error). The coroutine runs until it pauses, and what comes up is a Future. The task checks that it really is a future (asyncio marks them with a special flag). A bare None is also allowed and means "run me again next turn"; anything else is an error and adds its own wake-up callback to it. Then the step ends and the thread is free.

When the future is filled, its callbacks are scheduled with call_soon. The task's wake-up runs, and it calls the next step: send(None) again. The chain resumes at the exact await where it stopped. And when the coroutine finally returns, the task stores the return value as its own result, because a Task is a Future (we checked: isinstance(task, asyncio.Future) is True). That is why you can await a task to get its result.

56 · The example

asyncio.sleep(1), step by step

Here is the real path, from CPython's source:

1. sleep creates a future with loop.create_future(). 2. It asks the loop to fill it later: call_later(1, set_result_unless_cancelled, fut). 3. It awaits the future, which yields it up the chain to the task; the task attaches its wake-up callback; the step ends. 4. One second later the timer fires and fills the future. 5. The future schedules its callbacks; the task's wake-up calls send(None); sleep returns and your code continues. If the sleep is cancelled instead, a finally block cancels the timer so it never fires.

One special case: asyncio.sleep(0) creates no future at all. It does a bare yield, which the task treats as "reschedule me on the next turn". It is the cheapest way to let other tasks run.

57 · The socket version

How a network read waits

await loop.sock_recv(sock, 100) joins Act three to Act eight. It first simply tries sock.recv(100) on the non-blocking socket. If bytes are waiting, it returns them at once; no pause at all. Only if that raises BlockingIOError does it create a future, register the socket with the selector through add_reader, and await the future. When the selector reports the socket readable, the reader callback does the recv and fills the future with the bytes.

Watch the attempt bounce, the socket register, data arrive, and the future fill. Real libraries usually use a slightly different layer called transports and protocols, which keep a socket registered and push data in as it arrives, but the principle is identical: non-blocking socket, selector, future.

58 · A failure mode

A box nobody fills

A coroutine awaiting a future is paused until somebody fills that future. If nobody ever does (a callback that was never registered, a server that never answers, a bug), the task simply waits forever. Nothing errors. Nothing logs. The stage shows the box staying empty while the clock runs.

We demonstrated it safely: a future nobody fills, awaited inside asyncio.timeout(0.3). After 0.3 s the timeout gave up and cancelled the wait. That is the practical rule this teaches, expanded in Part 2: every wait on something outside your control needs a deadline.

59 · When does a task start?

create_task schedules; it doesn't run

asyncio.create_task(coro) wraps the coroutine in a Task and schedules its first step with call_soon. It does not run it. The child starts only when the current task reaches a real pause and hands the thread back. We checked: the order was "created", then "still running parent", then "child started".

This is why concurrency in asyncio comes from creating tasks before waiting, and why await coro and await create_task(coro) look similar but differ: the first runs the work inside your chain right now; the second makes an independent task that the loop will drive alongside everything else. (Python 3.12 added an opt-in "eager" mode that runs the first step immediately; it is covered in Part 2.)

ACT NINE

The event loop

Everything comes together: Act three's selector, Act four's callbacks, Act eight's futures and tasks, turned round and round by one loop.

62 · One turn of the loop

Wait, collect, run, repeat

The event loop holds three things: a ready queue of callbacks to run now, a timer heap of callbacks to run at a certain time, and a selector watching sockets. One turn of the loop (CPython calls it _run_once) does four things, and the hand on the stage sweeps through them.

1. Wait. Call select(). If anything is already ready, the timeout is zero: just check sockets and move on. Otherwise wait until the earliest timer is due, or, if there are no timers, until a socket is ready. 2. Collect I/O. For each ready socket, put its callback in the ready queue. 3. Collect timers. Move every timer whose time has come into the ready queue. 4. Run. Run the callbacks that were in the ready queue at the start of this phase; anything they schedule waits for the next turn, so a callback that keeps rescheduling itself can't starve the selector.

The loop's clock is a monotonic clock, one that never jumps backwards when the system time is adjusted.

63 · The cooperative rule

The loop cannot interrupt you

Step 4 runs a callback, and for a task that means one step of its coroutine, up to its next real pause. While that step runs, the loop is not running. There is no scheduler above it that can preempt it, as the OS does to threads. The ring stops turning until the step returns.

That is the whole contract of asyncio. The good side: between real pauses, no other task can touch your data, so most code needs no locks. The bad side: a step that takes a long time freezes every task. A time.sleep(0.5), a blocking requests.get, a big JSON parse or a heavy loop inside a coroutine all stop the ring. Timers fire late, sockets go unread, every other user waits. Watch the red bar jam the ring. Part 2 measures it and shows how to move such work off the loop.

64 · Timers

A heap: always know the earliest

The loop keeps timers in a heap, a structure that can always hand you the smallest item quickly without keeping the whole list sorted. So finding the next deadline is cheap even with thousands of sleeping tasks.

We scheduled callbacks with call_soon and call_later in a deliberate muddle. They ran: "soon 1", "soon 2", "later 0", "later 10ms": ready callbacks in order, then timers by deadline. Three tasks sleeping 0.3, 0.1 and 0.2 seconds woke in the order 0.1, 0.2, 0.3. Watch the tokens leave the heap.

A detail worth knowing: timers with exactly the same deadline are not run in the order you scheduled them. We scheduled twenty for the same instant and they ran 0, 2, 6, 14, 13, 19 and so on. A heap does not preserve insertion order for ties. Never rely on it; if order matters, chain the work explicitly.

65 · In code

A real event loop in 37 lines

This toy has a ready queue, a timer heap and a selector, and drives generator "tasks" that yield either ("sleep", seconds) or ("read", socket). The whole program is below; paste it and it runs. The stage replays its output.

import heapq, selectors, socket, time
from collections import deque

class Loop:
    def __init__(self):
        self.ready = deque()                 # callbacks to run now
        self.timers = []                     # heap of (when, n, callback)
        self.sel = selectors.DefaultSelector()
        self.n = 0
    def call_soon(self, cb):  self.ready.append(cb)
    def call_later(self, delay, cb):
        self.n += 1; heapq.heappush(self.timers, (time.monotonic() + delay, self.n, cb))
    def add_reader(self, sock, cb): self.sel.register(sock, selectors.EVENT_READ, cb)
    def run(self, *gens):
        for g in gens: self.call_soon(lambda g=g: self.step(g))
        while self.ready or self.timers or self.sel.get_map():
            while self.ready: self.ready.popleft()()                       # 1. run what's ready
            if not (self.timers or self.sel.get_map()): break             # nothing left to wait for
            timeout = max(0, self.timers[0][0] - time.monotonic()) if self.timers else None
            for key, _ in self.sel.select(timeout):                        # 2. wait for I/O or the next timer
                self.sel.unregister(key.fileobj); self.call_soon(key.data)
            while self.timers and self.timers[0][0] <= time.monotonic():   # 3. move due timers to ready
                self.call_soon(heapq.heappop(self.timers)[2])
    def step(self, g, value=None):                                         # a "task": drive a generator
        try: kind, arg = g.send(value)
        except StopIteration: return
        if kind == "sleep": self.call_later(arg, lambda: self.step(g))
        if kind == "read":  self.add_reader(arg, lambda: self.step(g, arg.recv(100)))

def sleeper(name, d):
    yield ("sleep", d); print(name, "woke")
def reader(sock):
    data = yield ("read", sock); print("reader got", data)

a, b = socket.socketpair(); a.setblocking(False)
loop = Loop(); loop.call_later(0.15, lambda: b.send(b"hello"))
loop.run(sleeper("A", 0.3), sleeper("B", 0.1), reader(a))
# 0.10 B woke · 0.15 reader got b'hello' · 0.30 A woke

The line with break has a story. Our first version lacked it, and after the last task finished the program hung forever: with no timers and nothing registered, select(None) waits for an event that can never come. Real loops face the same question, which is why asyncio.run stops when main finishes rather than when "nothing is left".

66 · The real thing

What asyncio.run does

asyncio.run(main()) is the one place sync code starts async code. It: 1. creates a fresh event loop; 2. wraps main() in a Task (we checked: inside main, current_task() is a Task); 3. turns the loop until that task finishes; 4. cancels any tasks still running (our forgotten background task printed "cancelled at exit"), finishes async generators, and shuts down the thread pool used for blocking calls; 5. closes the loop.

Rules that follow. Call it once, at the top of the program. You can't call it from code that is already inside a running loop: that raises RuntimeError: asyncio.run() cannot be called from a running event loop (Part 2 covers Jupyter, where this bites). Inside async code, get the current loop with asyncio.get_running_loop(); the older get_event_loop() warns when no loop is running (a DeprecationWarning on 3.12, verified) and newer versions are stricter still. To run several top-level calls on one loop, Python 3.11 added asyncio.Runner.

67 · Under the hood

Different loops for different systems

The loop you get depends on the platform. On Linux and macOS it is a selector loop built on epoll or kqueue (ours reported _UnixSelectorEventLoop). On Windows the default since Python 3.8 is the Proactor loop, built on I/O completion ports: instead of "tell me when I may read", it says "read into this buffer and tell me when done". It lacks a few selector-only methods such as add_reader, which some libraries need.

The loop is also replaceable. uvloop is a drop-in loop written on top of libuv (the engine under Node.js) that is often noticeably faster; on Python 3.12 and later you start it with uvloop.run(main()). Your coroutines don't change: they only ever see futures.

Nine things to remember

  1. asyncio is concurrency on one thread: it overlaps waiting, not computing.
  2. Threads are preempted anywhere; asyncio tasks switch only at real pauses.
  3. "Waiting for the network" means a non-blocking socket registered with a selector; blocking libraries hide their sockets and can't take part.
  4. A generator is a function whose frame survives; send, throw and yield from let an outside driver run a whole chain.
  5. Calling an async def runs nothing; it makes a coroutine object.
  6. await pauses only if something at the bottom of the chain really yields.
  7. At the bottom of every chain is a Future; a Task steps the coroutine and wakes when the future is filled.
  8. The loop runs callbacks; it can't interrupt one, so a blocking step freezes everything.
  9. asyncio.run starts it all, once, at the top.
