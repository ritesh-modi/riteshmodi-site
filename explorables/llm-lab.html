MISSION ONE

Your first call

Every chatbot, coding assistant and AI feature you have used is built on the same simple exchange: send a request, get a response. Let's see one with nothing hidden.

01 · The concept

A request is a small JSON message

An API (application programming interface) is a door that programs use to talk to a service. To use a model, your program sends an HTTP request to its address with a JSON body. JSON is just text in a structured format of names and values.

The body has three main parts. model: which model to use. messages: the conversation so far, as a list. Each message has a role: system for standing instructions, user for what the person says, and assistant for the model's earlier replies. And settings such as max_tokens (the longest answer you'll accept) and temperature (how random it should be).

Important: the model remembers nothing between calls. To have a conversation, your program resends the whole message list every time, adding the new turn at the end.

02 · The lab

Send a request and read everything that comes back

Type a message and press Send. You will see the exact JSON that went out, the answer, and the usage numbers: how many tokens your prompt used and how many the answer used. Tokens are what you are billed for, and Mission two is all about them.

+40 XPChallenge: get the model to answer with a haiku (three lines) about tokens. Change the system message, not just the user message.

03 · Streaming

Why answers appear word by word

With stream on, the API sends the answer in small pieces as soon as each is generated, using a format called server-sent events. Each piece usually holds a token or two. That is why chat apps show text appearing gradually: the model really is producing it one token at a time.

Turn streaming off and send again: the answer appears all at once, after the whole thing is generated. The total time is about the same. Streaming changes when you start seeing the answer, which matters a lot for how fast an app feels.

Look at finish_reason in the meta line. stop means the model chose to end. length means it hit max_tokens and was cut off mid-thought.

04 · Inputs and outputs

One call, in one block

in

model · messages (system, user, assistant) · settings like max_tokens and temperature.

out

The assistant's message · finish_reason · usage (prompt tokens, completion tokens).

meaning

The model is stateless: every call carries the whole conversation. Everything later on this page is built from this one exchange.

MISSION TWO

Tokens: what you really pay for

The usage numbers in Mission one were counted in tokens, not words or characters. Here is what a token is, and how to measure them yourself.

05 · The concept

Models read word pieces

Before a model sees your text, a tokenizer cuts it into tokens: common words become one token, rarer words are split into pieces, and spaces and punctuation usually ride along with a neighbour. For English, a token averages about three-quarters of a word.

Tokens matter for three reasons. Cost: providers charge per token, separately for input and output. Limits: the context window and max_tokens are counted in tokens. Behaviour: the model never sees letters, which is why it can stumble on spelling or counting characters.

Each model family has its own tokenizer, so the same text can be a different number of tokens on different models.

06 · The lab

Measure and see the split

Count sends your text and reads usage.prompt_tokens, minus a baseline measured once for the message wrapper, so you get the count for your text alone. Show split asks the model to repeat your text exactly and returns each output token, so you can see where the cuts fall (the model occasionally changes a character, so treat this as a close view rather than an exact one).

Lab · tokenizer

+40 XPChallenge: find a single word that costs 4 or more tokens. (Count it on its own.)
+40 XPChallenge: count a sentence in a language other than English. Is it more tokens than its English translation?

07 · Inputs and outputs

Tokens, in one block

in

Any text: English, other languages, code, emoji.

out

A sequence of tokens; common words are one token, rare words and many non-English scripts take more.

meaning

Cost, limits and some odd mistakes all come from tokens. Short, clear prompts are cheaper and often better.

MISSION THREE

Next word: watch the model choose

A language model writes by scoring every possible next token and picking one. The DeepSeek API can show you those scores. Let's look inside one decision at a time.

08 · The concept

Every step is a probability distribution

At each step, the model gives every token in its vocabulary a probability, and they add up to 100%. Setting logprobs: true and top_logprobs: 10 asks the API to return the ten most likely candidates at each position, with their log-probabilities. A log-probability is just a compact way to store small probabilities; the page converts it back with elogprob.

One surprise worth knowing: DeepSeek reports these probabilities after applying temperature. At temperature 0 the top token always shows as about 100% and everything else as 0%, which hides the real picture. So this lab asks at temperature 1, the model's natural distribution. Try "The capital of France is": even at temperature 1 it is nearly 100% "Paris". Then try "The cat sat on the" and see the model hesitate between "mat" and "windows".

The lab asks for one token at a time. The system message tells the model to continue your text, so its first token is effectively "the next word". Press Step to append the top choice and predict again: you are running the generation loop by hand.

MISSION FOUR

Temperature: the creativity dial

If the model always took the top token, it would be predictable and dull. Temperature controls how often it takes a less likely one.

11 · The concept

Temperature reshapes the probabilities before picking

Before sampling, each candidate's log-probability is divided by the temperature, and the probabilities are recalculated. At temperature 0 the top token always wins. At 1 the model samples from its natural distribution. Above 1, unlikely tokens get a bigger share, which brings more surprise and, eventually, nonsense.

Drag the slider: the stage reshapes the real distribution from your last Mission three run (taken at temperature 1, so dividing by your chosen temperature gives exactly what the API would sample from). DeepSeek accepts temperatures from 0 to 2. (In thinking mode temperature is ignored, so these labs turn thinking off.)

12 · Inputs and outputs

Choosing a temperature

in

A task and how much variety you want.

out

Low (0–0.3) for extraction, classification and facts · around 1 for normal writing · higher for brainstorming.

meaning

Even at temperature 0, providers don't promise identical outputs every time, so build checks for anything that must be exact.

MISSION FIVE

Prompt engineering, tested

"Write a better prompt" is vague advice. Here you will try six real techniques on one task and let an automatic grader score each one.

13 · Six techniques

What each technique adds

Zero-shot: just ask. Fine for easy, common tasks.
Role and rules: say who the model is and list the exact rules ("use one of these four labels, nothing else").
Delimiters: wrap the input in clear markers like <message>…</message>, so the model cannot confuse your instructions with the user's text. This also helps against prompt injection.
Few-shot: include a few solved examples. The model copies the pattern, including the format.
Chain of thought: ask it to reason briefly before the final answer. Helps on tricky cases, costs more tokens.
Structured output: ask for JSON and turn on response_format: json_object, so your code can read the answer reliably.

14 · The lab

Classify six support messages

The task: label each customer message as billing, technical, shipping or other. Some messages are deliberately ambiguous. Pick a technique to load its template, edit it if you like ({message} is replaced by each test message), and press Grade. The grader runs all six and checks the answers.

15 · Inputs and outputs

What you should have noticed

in

The same model and task, with different prompt techniques.

out

Different accuracy, different output formats, different token costs.

meaning

Clear rules and a fixed format fix most problems; examples fix format drift; reasoning helps ambiguous cases at a cost. Always measure on test cases instead of trusting one good-looking answer.

MISSION SIX

Reasoning: let it think first

DeepSeek's models can "think" before answering: they write out a hidden chain of reasoning, then give the final answer. Let's see what that buys and what it costs.

16 · The lab

Same puzzle, thinking off vs on

Thinking mode is on by default in the DeepSeek API, and is set with thinking: {type: "enabled"} or "disabled". When it is on, the reasoning comes back in a separate field, reasoning_content, next to the normal content. Run the puzzle both ways and compare the answer, the time and the tokens.

Lab · thinking

Show the model's reasoning
+60 XPChallenge: run the puzzle both ways and compare the token counts.

The correct answer is 9 (three in each word). Remember Mission two: the model sees tokens like "straw" and "berry", not letters, so counting letters in one shot is hard. With thinking on, it can spell each word out and count, which is exactly the kind of step-by-step work reasoning is for. When we tested this lab, thinking off sometimes answered 7, and sometimes got 9 only by writing its counting out in the visible answer; thinking on answered 9 every time, at the cost of a few hundred reasoning tokens. Run it a few times and see what you get.

17 · Inputs and outputs

When to pay for thinking

in

A question, plus thinking on or off.

out

With thinking: reasoning tokens plus the answer, slower and costlier, often more accurate on hard problems.

meaning

Turn thinking on for maths, logic, planning and tricky code. Turn it off for quick lookups, formatting and classification at scale.

MISSION SEVEN

Build a simple RAG

The model knows nothing about your company. Retrieval-augmented generation fixes that: find the relevant documents first, then let the model answer from them.

18 · The concept

Retrieve, then generate

RAG has two steps. Retrieve: score every chunk of your documents against the question and keep the best few. Generate: put those chunks in the prompt with an instruction like "answer only from these passages, cite them, and say if the answer isn't there".

Production systems usually retrieve with embeddings: vectors that capture meaning, so "money back" matches "refund". DeepSeek's API does not offer an embedding model, so this lab uses a simpler, classic method that runs right here in your browser: TF-IDF, which scores chunks by shared words, giving more weight to rare words. It is weaker on synonyms, which you may notice, and that is a lesson in itself.

The knowledge base below belongs to Pebble Cycles, a bike shop invented for this lab. The model cannot possibly know its policies, so any correct answer must come from retrieval.

MISSION EIGHT

Build an agent

Now the model gets hands. You will run a customer-support agent for Pebble Cycles that can look up orders, check policy, and issue refunds, but only with your approval.

21 · The concept

Tools, a loop, and a gate

The agent is the model plus four tools, described to it in JSON: lookup_order(order_id), get_policy(topic), issue_refund(order_id, amount, reason) and reply_to_customer(text). When the model wants a tool, the API returns a tool call instead of an answer. This page's JavaScript runs the tool on a small fake database, sends the result back, and loops.

Three safety rules live in the code, not in the prompt: at most 8 steps; a refund can never exceed the order total; and every refund stops at an approval gate where you click Approve or Reject.

One order has a nasty surprise in its notes field: a hidden instruction trying to trick the agent. Watch what happens.
