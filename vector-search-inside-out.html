Vector Search Inside Out:
HNSW from first principles

Every "find similar" feature, from semantic search to the retrieval step in a chatbot, ends in the same question: which of my millions of stored vectors are closest to this one? HNSW is the algorithm almost every vector database uses to answer it in a fraction of a millisecond. This book opens it up, one step at a time, in 92 figures, and then tunes it on 1.18 million real vectors.

Search by walking, not by scanning

The obvious way to find the ten closest vectors is to measure the distance to every stored one and keep the smallest. It is correct, and at a million vectors behind a search box it is too slow. HNSW measures only a few hundred instead. It links every point to a few nearby points, and a search walks those links towards the query, one hop at a time, the way you would find a street in an unfamiliar town by asking each passer-by to point you a little closer.

A walk that only ever steps closer has a flaw. It can stop at a point whose neighbours are all farther away, while the true nearest point sits just out of reach.

The fix is to keep several candidates alive at once. A short, sorted list of the best points found so far, its size called ef, lets the search keep exploring around the others when one path dead-ends. With a list of four, the same query finds the true nearest point.

Start close, then search wide

A beam is only as good as its starting point. HNSW stacks ever-sparser copies of the graph on top of each other, like flights, trains and buses on the way to a friend's house: a query crosses the map in a few long hops on the upper layers, then drops to the bottom layer already among its nearest neighbours, and the beam finishes the job.

What the book covers

  • What nearest-neighbour search is, and when you do not need HNSW. Recall, the ground truth that measures it, and the honest cases where batched exact search beats any index.
  • Walking a graph instead of scanning a list. Greedy routing, the local minimum that traps it on about one query in eight, and the small-world links that make walks short.
  • The beam, the layers and a search from start to finish. How a beam of width ef rescues a stuck walk, why the index has layers, and how one query descends them to its ten nearest neighbours.
  • How the index chooses links and builds itself. The neighbour heuristic that keeps the bridges between clusters, and insertion as one search per point, threads and all.
  • Every knob, measured on real data. M, efConstruction and ef on 60,000 Fashion-MNIST images and 1.18 million GloVe vectors, with a five-step tuning recipe for your own collection.
  • What production adds. Recall at scale, memory and quantisation with re-ranking, filters that cost 75 times the latency, deletes, distances, and what nine databases call each knob.

Written for engineers who build search and retrieval on vector databases and want to know what their index is doing. You need basic Python and a rough idea of what an embedding is; no graph theory or maths beyond distances. A sequel in spirit to Inside asyncio, in the same Forward Deployed Engineer Series.
